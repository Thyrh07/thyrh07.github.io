## **<span style='color:#ff5555'>Ringkasan</span>**
***

Java4Shell adalah kerentanan memory corruption di decoder Base64 OpenJDK yang memungkinkan remote code execution (RCE) — dalam banyak kasus tanpa autentikasi — pada aplikasi Java enterprise yang banyak dipakai. Kerentanan ini diungkap 17 November 2026 oleh peneliti keamanan Calif, dan patch-nya dirilis Oracle dan OpenJDK di hari yang sama.

- **CVE:** CVE-2026-114938
- **Nama:** Java4Shell
- **Jenis:** Heap-based out-of-bounds write di HotSpot JVM, decoder Base64 yang dipercepat AVX-512 VBMI
- **Skor:** CVSS 4.0 **9.2 (Critical)** menurut Calif; CVSS 3.1 **8.1 (High)** menurut Oracle
- **Penemu:** Quang Luong dari Calif, dibantu OpenAI Codex — ditemukan dalam sekitar satu jam, exploit awal dibuat dalam dua jam berikutnya, dengan biaya AI kurang dari $200
- **Pemicu:** Input Base64 malformed sepanjang 65 karakter — 64 karakter `A` diikuti `=` — yang menulis 62 byte melewati buffer output
- **Terdampak:** OpenJDK 17.0.6 dan yang lebih baru, pada Java 17, 21, 25, dan 27, di CPU x86-64 dengan AVX-512 VBMI
- **Tidak terdampak:** ARM64, x86-64 tanpa AVX-512 VBMI, serta OpenJDK 8 dan 11 standar
- **Status eksploitasi:** Probing sudah teramati per 20 November 2026 (197 request berbentuk serangan dari 7 IP, GreyNoise); belum ada intrusi yang berhasil terkonfirmasi; belum masuk CISA KEV per 20 Nov 2026

> **Update 20 Nov 2026 — probing sudah teramati, belum ada intrusi:** GreyNoise mencatat 197 request berbentuk serangan Java4Shell dari 7 IP, probing sudah merambah endpoint Jenkins (naik dari 150+ request / 5 IP per 19 Nov). Tetap belum ada intrusi yang berhasil terkonfirmasi, dan Java4Shell belum masuk CISA KEV per 20 Nov.

> ⚠ **Klarifikasi penting:** Java4Shell bukan malware dan bukan satu exploit universal. Calif mendemonstrasikan RCE pada aplikasi tertentu dengan konfigurasi default, tetapi exploit per produk berbeda-beda dan Calif menahan exploit weaponized-nya. Keberadaan kerentanan ini tidak dengan sendirinya membuktikan setiap instalasi aplikasi yang disebutkan bisa dieksploitasi.

## **<span style='color:#ff5555'>Apa Itu Java4Shell</span>**
***

Java4Shell adalah bug di `java.util.Base64.Decoder` — jalur yang dipercepat oleh intrinsic AVX-512 VBMI di HotSpot JVM x86-64.

Base64 adalah cara umum menulis data sebagai teks. Server Java mendekode Base64 setiap saat: header HTTP Basic yang membawa username dan password, artefak SAML single sign-on, token CSRF, JWT, dan tiket aplikasi. Karena decoding itu sering terjadi sebelum pemeriksaan login selesai, input berbahaya bisa mencapai decoder lewat request tanpa autentikasi.

Bug-nya ada di assembly hand-written yang mempercepat decoding dengan instruksi AVX-512 VBMI:

- Saat input Base64 berakhir dengan satu karakter padding `=` yang berlebih, perhitungan panjang output mengalami underflow
- Decoder kemudian menulis satu write selebar penuh melewati akhir array output — **62 byte melewati buffer** pada build dan prosesor yang terdampak (pada build Java 17 yang lebih lama, pemicunya 128 karakter `A` diikuti `=`)
- Java memang menolak input itu — tetapi hanya setelah write terjadi. Kerusakan heap sudah terjadi dan tidak dibatalkan oleh exception
- Byte yang ditulis melewati batas itu bernilai tetap, sehingga penyerang tidak langsung mengontrol isinya — penyerang mengakalinya dengan mengatur layout heap server, sehingga overflow itu memperbesar array tetangga, lalu memakai array itu untuk menulis byte pilihannya sendiri

Calif menyebut tahap bocornya memori heap ini **JavaBleed**: dengan merusak panjang array tetangga, lebih banyak heap disalin kembali ke respons normal aplikasi, sehingga penyerang bisa membaca isi heap Java — yang bisa berisi PII, private key, secret key, dan token — bahkan sebelum eksekusi kode tercapai.

Jalur yang rentan hanya dipilih setelah JIT compiler mengompilasi decoder Base64 untuk kecepatan, jadi exploitability bergantung pada CPU, konfigurasi JVM, dan bagaimana aplikasi memproses input yang dikontrol penyerang.

## **<span style='color:#ff5555'>Aplikasi yang Terdampak</span>**
***

Calif mendemonstrasikan RCE pada aplikasi dengan konfigurasi default. Daftar ini tidak lengkap, dan hasil ini adalah hasil pengujian Calif sendiri — belum dikonfirmasi secara independen.

### RCE Tanpa Autentikasi (Pre-Auth)

| Aplikasi | Keterangan |
|----------|------------|
| Keycloak | Identity / SSO |
| Atlassian Jira | Issue tracking |
| Atlassian Confluence | Kolaborasi / wiki |
| JFrog Artifactory | Artifact repository |
| Jenkins | CI/CD |
| PingFederate | Identity / SSO |

### RCE Setelah Autentikasi (Post-Auth)

| Aplikasi | Keterangan |
|----------|------------|
| Apache Kafka Broker | Messaging |
| Apache Solr | Search |
| Elasticsearch | Search / analytics |
| Gerrit | Code review |
| Spinnaker (Netflix) | Continuous delivery |

Calif juga berhasil mengeksploitasi kerentanan ini pada aplikasi contoh yang dibangun dengan Apache Struts dan Spring Boot, serta melaporkan exploit client-side terhadap program Java yang terhubung ke server TLS berbahaya — jadi klien Java yang terhubung ke server yang tidak dipercaya juga berisiko, bukan hanya server.

Tidak ada exploit universal: tergantung bagaimana aplikasi memakai Base64 dan cara kerjanya, langkah yang berbeda mungkin diperlukan untuk tiap aplikasi.

## **<span style='color:#ff5555'>Versi yang Terdampak dan yang Sudah Diperbaiki</span>**
***

### Kondisi yang Harus Terpenuhi

Semua kondisi berikut relevan untuk keterjangkauan kerentanan:

1. **Build rentan:** service berjalan di JVM yang berisi intrinsic Base64 yang belum di-patch
2. **Prosesor yang memenuhi syarat:** runtime berjalan di x86-64 dengan AVX-512 VBMI — Intel Xeon Ice Lake dan yang lebih baru (Sapphire Rapids, Emerald Rapids, Granite Rapids), AMD EPYC dan Ryzen Zen 4 atau yang lebih baru. Di Linux, keempat flag `avx512f`, `avx512bw`, `avx512vbmi`, dan `bmi2` harus ada di `/proc/cpuinfo`
3. **Intrinsic rentan aktif:** intrinsic Base64 HotSpot dan jalur AVX-512 yang diperlukan belum dimatikan
4. **Data yang dikontrol penyerang mencapai decoder:** aplikasi atau library mendekode Base64 yang tidak tepercaya lewat jalur runtime yang terdampak

### Versi Terdampak

| Java release line | Terdampak | Diperbaiki (upstream) |
|-------------------|-----------|-----------------------|
| Java 17 | 17.0.6 dan yang lebih baru (belum di-patch) | **17.0.21.1** |
| Java 21 | Build belum di-patch | **21.0.13.1** |
| Java 25 | Build belum di-patch | **25.0.5.1** |
| Java 27 | Build belum di-patch | **27.0.1.1** |
| Oracle Java SE 8 Enterprise Performance Pack | 8u511b33-perf | 8u513-perf |

Distribusi yang dibangun dari kode yang terdampak antara lain: Oracle Java SE, Amazon Corretto, Eclipse Temurin, Microsoft Build of OpenJDK, Azul Zulu, BellSoft Liberica, SAP SapMachine, Red Hat OpenJDK, dan Oracle GraalVM for JDK. Kehadiran dan ketersediaan patch bersifat vendor- dan build-specific — memperbarui library aplikasi tanpa mengganti JVM yang dibundel tidak memperbaiki kerentanan ini.

## **<span style='color:#ff5555'>Teknis: Bagaimana Overflow Terjadi</span>**
***

1. Aplikasi menerima input yang dikontrol penyerang dan meneruskannya ke `java.util.Base64.Decoder` — misalnya kredensial HTTP Basic, artefak SAML, token CSRF, JWT, atau segmen upload
2. JIT mengompilasi decoder ke jalur AVX-512 VBMI yang dipercepat hardware
3. Input malformed — 64 karakter `A` diikuti `=` — membuat perhitungan panjang output underflow, sehingga store mask yang salah menghasilkan satu write selebar penuh melewati akhir output yang didekode
4. Decoder menolak input itu, tetapi heap sudah rusak: 62 byte tertulis melewati buffer
5. Dengan mengatur layout heap, penyerang memperbesar array tetangga (JavaBleed) untuk membaca heap, lalu memakai array kedua untuk menulis byte pilihannya dan mencapai eksekusi kode dengan hak proses Java yang terdampak

Lab lain sejauh ini baru mereproduksi crash dan memory leak, bukan eksekusi kode. Upwind mereproduksi overflow pada instance AWS c6i (Intel Ice Lake), di mana overflow itu merusak objek berikutnya di memori dan akhirnya membuat Java crash. Blackpoint Cyber membuat aplikasi Spring Boot test crash dengan sekitar 28.000 request login malformed dalam waktu sekitar 20 detik, tanpa pernah login.

## **<span style='color:#ff5555'>Deteksi dan Mitigasi</span>**
***

### 1. Patch Segera — Remediasi Utama

- Update runtime Java yang terdampak ke build yang sudah diperbaiki: **17.0.21.1, 21.0.13.1, 25.0.5.1, dan 27.0.1.1** (upstream); konsultasikan advisory distribusi untuk package yang sesuai
- Amazon Corretto: **17.0.21.1.2, 21.0.13.1.2, 25.0.5.1.2, dan 27.0.1.1.4**, dirilis 17 November 2026
- Prioritaskan aplikasi yang menghadap internet, infrastruktur identity, layanan CI/CD, dan service Java yang memproses Base64 yang tidak tepercaya
- Rebuild image container dan redeploy workload; pastikan semua proses Java sudah restart ke runtime yang sudah diperbaiki
- Oracle merilis patch ini pada 17 November 2026 sebagai bagian dari November Critical Security Patch Update, yang memperbaiki 655 kerentanan keamanan di seluruh portofolio produknya

### 2. Mitigasi Sementara Bila Patch Tertunda

Jalankan JVM HotSpot yang terdampak dengan salah satu flag berikut (sementara saja — patch tetap remediasi permanen):

```
-XX:-UseBASE64Intrinsics
```

Flag ini secara selektif mematikan decoding Base64 yang dipercepat hardware dan umumnya lebih disukai. Alternatifnya, hanya di x86-64:

```
-XX:UseAVX=2
```

Flag ini mematikan penggunaan AVX-512 secara lebih luas dan bisa berdampak pada performa; flag ini bisa gagal start di JVM ARM64. Validasi dukungan vendor, tambahkan opsi yang dipilih ke konfigurasi startup JVM service / container yang sebenarnya, restart proses Java, dan verifikasi flag efektifnya.

### 3. Kurangi Permukaan Serangan

- Bila memungkinkan, batasi akses publik ke service Java yang belum di-patch dan antarmuka administratifnya
- Validasi dan batasi input Base64 di batas aplikasi, terapkan batas ukuran, dan kurangi fungsionalitas tanpa autentikasi — ini adalah defence-in-depth, bukan mitigasi menyeluruh
- Jangan menganggap request buffering, aturan WAF, terminasi TLS, atau library Java yang sudah di-patch bisa mencegah eksploitasi JVM yang terdampak

### 4. Deteksi dan Investigasi

Perhatikan tanda-tanda berikut (tanda ini adalah petunjuk investigasi, bukan IOC yang tervalidasi untuk CVE-2026-114938):

- Crash atau restart JVM yang tidak biasa, log `hs_err_pid`
- Burst error `IllegalArgumentException` dari decoder Base64, terutama token Base64 panjang yang berakhir dengan `=`
- Child process yang tiba-tiba muncul, scheduled task baru, atau artefak web-shell
- Koneksi outbound yang aneh, perubahan file aplikasi atau secret yang tidak bisa dijelaskan
- Korelasikan log aplikasi, reverse proxy, autentikasi, host, dan endpoint

Bila sebuah instance bisa dijangkau saat belum di-patch, tinjau tanda-tanda penyalahgunaan dan rotasi kredensialnya bila kompromi tidak bisa dikesampingkan. Patching tidak membatalkan kompromi yang sudah terjadi sebelumnya.

### Cara Cek Cepat

```bash
# Versi Java yang dipakai proses yang sebenarnya (bukan java default sistem)
java -version
readlink -f "$(command -v java)"
ps -eo pid,args | grep '[j]ava'

# Cek dukungan CPU AVX-512 VBMI (keempat flag harus ada)
grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'
```

Jangan menjalankan test exploit atau pemicu crash yang tersedia publik terhadap service produksi sebagai metode inventarisasi.

## **<span style='color:#ff5555'>Kesimpulan</span>**
***

Java4Shell berbahaya bukan karena ia adalah malware atau exploit yang sudah tersebar — melainkan karena ia ada di runtime yang dipakai bersama oleh ribuan aplikasi, dan pemicunya bisa sampai ke decoder sebelum login diperiksa. Satu string Base64 sepanjang 65 karakter sudah cukup untuk merusak heap; sisanya adalah soal mengatur layout memori aplikasi target.

Tiga syarat harus terpenuhi sekaligus: build Java yang rentan, CPU x86-64 dengan AVX-512 VBMI, dan input Base64 yang dikontrol penyerang mencapai decoder. Bila salah satu tidak terpenuhi, jalur ini tidak bisa dieksploitasi — tetapi jangan jadikan itu alasan menunda patch. Periksa runtime Java yang sebenarnya dipakai tiap proses, update ke build yang sudah diperbaiki, dan restart semua JVM.
