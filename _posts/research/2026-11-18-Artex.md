## **<span style='color:#ff5555'>Ringkasan</span>**
***

ARTEX adalah framework penetration testing otonom berbasis LLM (Large Language Model) yang awalnya dibuat untuk pengujian keamanan yang sah — dan dalam hitungan minggu setelah dirilis, dipersenjatai oleh pelaku ancaman untuk serangan nyata. Ini bukan malware dalam arti klasik: ARTEX tidak punya model AI sendiri, tidak punya satu payload tunggal, dan tidak terikat ke satu CVE. ARTEX adalah **harness multi-agent**: ia mengubah tujuan yang ditulis dalam bahasa natural menjadi perintah, menjalankan tools keamanan, lalu merangkai hasilnya menjadi serangan — dari reconnaissance sampai eksfiltrasi data — dengan intervensi manusia yang minimal.

- **Apa itu:** Framework pentest agentic open-source, ditulis dalam Go, dengan frontend Next.js
- **Pembuat:** Li Puhua, dikenal sebagai Autumn-27, engineer keamanan asal Tiongkok
- **Dirilis:** Juli 2026 di GitHub, lisensi AGPL-3.0
- **Status:** Repository GitHub dan Docker image ditarik / dibuat privat pada 8 Oktober 2026, dengan penghapusan Docker pada 11 Oktober 2026 — tetapi fork, mirror, dan salinan yang sudah diunduh tetap beredar, plus versi komersial ARTEX PRO
- **Korban yang dikaitkan:** 7 institusi keuangan Korea Selatan, ratusan organisasi global lewat kampanye Storm-0940 / ConnectWise, dan 200+ organisasi lewat Vapor Panda
- **Kecepatan yang dilaporkan:** Dari target awal ke privileged access dalam waktu kurang dari 3 jam pada beberapa intrusi
- **Zero-day yang digunakan:** Tidak ada yang dilaporkan oleh sumber mana pun — serangan mengandalkan kelemahan yang sudah dikenal, dengan kecepatan mesin

> ⚠ **Klarifikasi penting:** ARTEX sering disebut "malware ARTEX" di pemberitaan, tetapi secara teknis ia adalah **framework dual-use**. Yang membuatnya berbahaya bukan satu exploit, melainkan otomasi: satu operator bisa menjalankan banyak kampanye sekaligus, 24 jam, dengan kecepatan yang tidak bisa diikuti manusia.

## **<span style='color:#ff5555'>Apa Itu ARTEX</span>**
***

ARTEX adalah sistem multi-agent yang menjalankan penetration test secara otonom, dari reconnaissance sampai data exfiltration, dengan sedikit interaksi manusia. Agent-agentnya mengakumulasi aset dan kerentanan yang ditemukan ke dalam sebuah graph selama pengujian berlangsung.

Arsitekturnya, menurut Microsoft dan FBI:

- **Multi-agent LLM system** — satu Planner / agen utama mengoordinasikan banyak Worker Agent
- **ARTEX v2** — menggunakan Central Planner untuk mengoordinasikan beberapa Worker Agent, menurut AhnLab
- **Ditulis dalam Go**, frontend Next.js, UI default berbahasa Inggris dan bisa dialihkan ke Korea, Mandarin, Spanyol, atau Jepang
- **Tidak membawa model sendiri** — ia terhubung ke penyedia LLM eksternal: Anthropic Claude, OpenAI GPT, DeepSeek, GLM, Grok, dan Kimi
- **Guardrail bawaan yang lemah** — default blocklist-nya memblokir target instansi pemerintah dan universitas, tetapi **institusi keuangan tidak ada di daftar itu**

Dalam waktu 10 minggu setelah rilis, ARTEX mencapai perkiraan **1.500–2.000 GitHub stars**, menurut FBI FLASH-20261113-001.

### Model LLM yang Teramati

| Model | Peran yang dilaporkan |
|-------|------------------------|
| DeepSeek v4.1 Flash | Model utama di kampanye Korea Selatan |
| GLM-5.3 (Zhipu AI) | Model cadangan |
| Grok 4.6 | Model cadangan |
| Claude Code 2.1.221 | Harness yang dipakai operator di kampanye Korea Selatan — 510 kali dijalankan sejak 4 Agustus 2026, tetapi tidak berbicara langsung ke API Anthropic |

Rute model itu penting untuk deteksi: di infrastruktur Korea Selatan, request Claude Code dialihkan lewat Claude Code Router (CCR) dan shim lokal ke reseller `xcai[.]pro`, lalu ke DeepSeek. Hunt.io menemukan 19 custom skills di file `.claude.json` operator, dengan total 147 kali pemakaian — mencakup code audit, reconnaissance, web injection, WAF bypass, authentication testing, Telegram Mini Apps, download dan decompile APK, cloud phone control, dan payment logic testing.

## **<span style='color:#ff5555'>Kampanye yang Dikaitkan dengan ARTEX</span>**
***

### 1. Bank Korea Selatan — September–Oktober 2026

Antara akhir September dan awal Oktober 2026, **tujuh institusi keuangan Korea Selatan** mengalami breach data lewat sistem internet-facing di pinggiran (peripheral systems), bukan core banking.

- **Korban terdampak:** sekitar **66.000–68.000 individu** dan sekitar **2.200 korporasi**
- **Data yang bocor:** data pribadi, pekerjaan, penghasilan, dan pinjaman — termasuk nama, resident registration number, income, loan limits, dan employer
- **Jalur masuk:** bukan zero-day. ARTEX merayapi situs dan mem-parsing HTML / JavaScript untuk menemukan API di baliknya, lalu menargetkan broker loan-status API, backend aplikasi mobile karyawan (relationship manager / private banker), dan halaman pencarian recruiter
- **Pola serangan:** setiap request terlihat seperti panggilan API yang sah, dengan ID yang masuk akal — tidak ada payload malicious di request itu sendiri. Yang abnormal adalah volume dan pola lookup berurutan
- **Publikasi:** CrowdStrike 7 Oktober 2026, Genians Security Center 12 Oktober 2026
- **Atribusi operator:** CrowdStrike menilai dengan moderate confidence bahwa operatornya adalah **satu individu berbahasa Tiongkok yang termotivasi finansial**, bukan kelompok ancaman yang sudah mapan

Infrastruktur yang teridentifikasi publik: server **38.244.50[.]120** yang meng-host ARTEX console, plus alamat Hong Kong dan sembilan proxy. Hunt.io kemudian menemukan jump server kedua di **23.248.226[.]250** (Hong Kong), dengan open directory berisi konfigurasi, script tunnel SSH reverse, dan kredensial untuk Zhipu AI / GLM, relay OpenAI-compatible, dan proxy service.

### 2. Storm-0940 dan ConnectWise — September–Oktober 2026

Microsoft melaporkan bahwa Storm-0940, aktor yang selaras dengan negara Tiongkok dan aktif sejak 2021, menggunakan ARTEX sejak September 2026 untuk mengotomasi serangan ke **ratusan organisasi global** di berbagai industri.

- **Supply chain:** Storm-0940 bertanggung jawab atas kompromi ConnectWise Cloud Backup, aplikasi multi-tenant
- **Skala downstream:** percobaan sign-in ke **lebih dari 2.250 tenant Microsoft 365** lewat kredensial aplikasi ConnectWise yang sudah dicuri
- **Password spraying:** 10–14 Oktober 2026, infrastruktur **144.172.64[.]99** melakukan password spray lintas tenant ke **327 akun di 8 organisasi**, dengan **151.000+ failed logon**, puncak **2.900 kegagalan per menit** pada 11 Oktober, dan lebih dari 111.000 kegagalan dalam satu hari
- **Kecepatan:** beberapa intrusi bergerak dari target awal ke privileged access dalam **kurang dari 3 jam**
- **Follow-on:** lewat Microsoft Graph, agent melakukan reconnaissance, perubahan kredensial aplikasi, dan upaya modifikasi privilege untuk persistence — tanpa perlu sign-in interaktif dari pengguna

Microsoft menegaskan aktivitas ini bukan hasil kompromi atau kerentanan di sistem korporat Microsoft. Kehadiran aplikasi yang terdampak, atau autentikasi yang berhasil, tidak dengan sendirinya membuktikan data pelanggan diakses atau dieksfiltrasi.

### 3. Vapor Panda, Storm-3358, dan Kampanye Lain

- **Vapor Panda (CrowdStrike):** satu controller ARTEX menargetkan **200+ organisasi di sedikitnya 14 negara selama 11 hari** mulai 17 Oktober 2026, dengan post-exploitation terkonfirmasi di sembilan organisasi
- **Storm-3358 (Microsoft, 6 November 2026):** menggunakan ARTEX untuk mengeksploitasi anonymous file upload dan SSRF di sistem internet-facing, lalu memasang remote access trojan
- **Kelompok kriminal berbasis Kamboja (Microsoft, 6 November 2026):** menggunakan ARTEX terhadap organisasi keuangan, sebagian besar di Asia Tenggara, plus sejumlah kecil organisasi keuangan besar secara global
- **Skala paparan:** FBI mencatat **lebih dari 1.600 instance console ARTEX yang terekspos publik** pada awal November 2026. Check Point menemukan **2.557 sistem** yang meng-host atau pernah meng-host panel ARTEX, dengan **1.608 instance live** saat penelitian. Censys dan peneliti lain menemukan angka yang sejalan

## **<span style='color:#ff5555'>Teknis: Bagaimana ARTEX Bekerja</span>**
***

```
[Tujuan dalam bahasa natural]
     │
     ├── Planner / agen utama memecah tujuan menjadi tugas
     ├── Worker Agents mengeksekusi tugas secara paralel
     │   ├── Recon: crawl situs, parse HTML/JS, temukan API tersembunyi
     │   ├── Enumerasi: fuzzing direktori, WHOIS, vulnerability scanning
     │   ├── Eksploitasi: SQL injection, auth bypass, SSRF, file upload,
     │   │   command injection, SSTI, IDOR
     │   ├── Persistence: web shell JSP/PHP, RAT open-source
     │   │   (WISP, vshell, AdaptixC2), SSH key, OAuth credential
     │   └── Eksfiltrasi: query database, baca blob, staging data
     │
     └── Hasil diakumulasi ke graph aset + kerentanan
         └── Laporan / langkah berikutnya dipilih oleh agent
```

Yang membedakan ARTEX dari scanner biasa adalah **rantai otomatis**: agent tidak berhenti di satu temuan. Ia menguji kredensial yang dicuri, memetakan permission cloud (SAS token, Service Principal, Kudu credential, Storage Account key) dalam waktu sub-detik, lalu mencoba pivot ke sistem lain — termasuk lewat trust relationship vendor dan supply chain.

Contoh kemampuan yang tercatat di FBI FLASH dan laporan Mandiant / Google Threat Intelligence:

- **Recon cloud:** capability check permission Azure, test blob write/delete, ARM deployment validation dry-run
- **Initial access:** unsigned SAML assertion, XXE, anonymous file upload, SSRF, hardcoded admin password di bundle JavaScript SPA, API tanpa autentikasi, RCE lewat command injection / SSTI / SQL injection
- **Persistence:** web shell JSP/PHP (termasuk lewat MySQL log poisoning), penyalahgunaan Kudu admin API, C2 di Windows database server internal, RAT open-source
- **Privilege escalation:** Kerberoasting, DCSync untuk mencuri krbtgt key, pembuatan akun dengan flag `is_admin=true`, resource-based constrained delegation, query cloud metadata service lewat XXE
- **Internal recon:** enumerasi **lebih dari 110.000 objek Active Directory** dalam satu kasus, baca password LAPS, inventarisasi coverage endpoint sensor untuk mencari mesin tanpa CrowdStrike Falcon
- **Eksfiltrasi:** interrogasi database SQL backend, mass blob read, boot script kustom via EC2 untuk harvest data, output command dikirim ke rotating webhook.site endpoint, baca mailbox di mail server yang dikompromikan

## **<span style='color:#ff5555'>Deteksi</span>**
***

Sinyal yang perlu dimonitor:

1. **Volume dan kecepatan yang tidak manusiawi** — ratusan hingga ribuan request / failed logon dalam hitungan menit, dari IP yang sama, dengan perubahan iteratif yang kecil antar percobaan
2. **Sequential enumeration** — lookup berurutan terhadap endpoint login / search / API, dengan jumlah record per sesi yang jauh di atas normal
3. **User-Agent dan artefak framework** — `scopeweaver`, `artex-enrich/1.0`, `Mozilla/5.0 (spa-api-recon)`, serta pemanggilan fungsi JSON seperti `list_findings`, `record_fact`, dan `shell_send`
4. **Outbound ke LLM API yang tidak biasa** — `api.anthropic.com`, `api.deepseek.com`, `open.bigmodel.cn`, `api.x.ai`, atau reseller / proxy LLM yang tidak dikenal, dari server atau workload yang seharusnya tidak memanggil LLM
5. **Perubahan kredensial aplikasi** — penambahan kredensial ke OAuth app yang sudah ada, app-role assignment, consent grant, dan perubahan privileged role — terutama dari service principal, bukan user interaktif
6. **Web shell di path yang tidak wajar** — file `*.aspx` atau `*.jsp` di direktori web yang tidak seharusnya
7. **Aktivitas Graph / Entra yang anomali** — reconnaissance lewat Microsoft Graph, listing direktori / permission / approval dari IP yang tidak dikenal

Contoh hunting di log:

```bash
# Cari pola password spray lintas tenant / akun
# - banyak failed logon dari satu IP dalam waktu singkat
# - 2.900+ kegagalan per menit adalah pola yang dilaporkan Microsoft

# Cari User-Agent ARTEX / ScopeWeaver di log web / proxy
grep -Ei 'scopeweaver|artex-enrich|spa-api-recon' /var/log/nginx/access.log

# Cari outbound ke LLM API dari workload yang tidak seharusnya
# api.deepseek.com, open.bigmodel.cn, api.x.ai, xcai.pro

# Cari penambahan kredensial OAuth / service principal di audit log
# - credential additions, app-role assignments, consent grants
# - privileged role assignments yang tidak ada change ticket-nya
```

> ⚠ **Penting:** Sebuah console ARTEX yang terekspos publik tidak dengan sendirinya membuktikan aktivitas kriminal. Beberapa instance adalah lab, penelitian, atau pengujian yang sah. Korelasikan IOC dengan aktivitas lain — volume, pola, dan perubahan kredensial — sebelum mengambil tindakan blocking.

## **<span style='color:#ff5555'>Mitigasi</span>**
***

### 1. Kurangi Attack Surface Eksternal

- Inventarisasi **semua** aplikasi internet-facing, termasuk portal partner / supplier, backend mobile, aplikasi karyawan, sistem legacy, dan integrasi pihak ketiga — bukan hanya aplikasi flagship
- Batasi admin cloud, Kudu / SCM endpoint, hypervisor, dan platform backup hanya ke jaringan tepercaya atau jalur admin khusus
- Nonaktifkan basic publishing authentication jika tidak diperlukan, dan batasi akses SCM ke jaringan manajemen yang disetujui
- Pindahkan aplikasi enterprise ke balik Zero Trust access jika memungkinkan

### 2. Keraskan Identitas dan Akses

- Terapkan least privilege untuk permission aplikasi multi-tenant dan consent grant
- Monitor penambahan kredensial, privilege assignment, dan aktivitas app-only yang anomali — terutama ke aplikasi dengan permission tinggi
- Review semua tenant Microsoft 365 tempat aplikasi ConnectWise yang terdampak pernah diinstall / diautorisasi, cari berdasarkan application ID, bukan display name
- Review sign-in service principal yang berhasil dan gagal secara terpisah, dan jangan batasi pencarian hanya ke IP yang dipublikasikan
- Rotasi kredensial yang terekspos, dan hapus kredensial / grant / owner / assignment yang tidak sah setelah evidence diamankan

### 3. Keraskan API Bisnis

- Pasang guardrail di API berdampak tinggi: rate limit, recipient limit, transaction threshold, dan abuse control yang sesuai fungsi
- Alert saat aplikasi beroperasi jauh di luar volume normal, dan saat ada sequential lookup atau jumlah record per sesi yang tidak wajar di portal partner / karyawan
- Enforce server-side authorization untuk akses ke record pelanggan, dan batasi response hanya ke field yang dibutuhkan operasi itu
- Jangan kembalikan stack trace, pesan SQL error, internal path, atau detail framework ke user yang tidak terautentikasi
- Scan repository, container image, build artifact, dan pipeline secara kontinu untuk secret yang terekspos, dan rotasi kredensial yang bocor segera

### 4. Jangan Unduh Salinan ARTEX dari Sumber Tidak Resmi

Beberapa salinan ARTEX tidak resmi di GitHub dan Docker Hub dilaporkan **backdoored** — misalnya image dengan routine `verifyCaptcha()` tersembunyi yang menjalankan input berawalan secret marker lewat `sh -c` sebagai root sebelum autentikasi apa pun. Satu image yang dilaporkan memiliki sekitar 9.000 download, dan 62 console tercatat melayani build backdoored itu antara 2–4 November 2026.

Jangan mengunduh atau menjalankan framework ini di luar lab yang terisolasi dan terotorisasi, dan jangan pernah menjalankannya terhadap sistem yang bukan milik Anda atau yang tidak Anda miliki otorisasi tertulis untuk diuji.

## **<span style='color:#ff5555'>Kesimpulan</span>**
***

ARTEX bukan ancaman karena satu exploit baru. Ancamannya adalah **kecepatan dan skala**: agent AI bisa merantai teknik yang sudah dikenal — SQL injection, auth bypass, password spraying, penyalahgunaan OAuth — dalam hitungan jam, terhadap ratusan target sekaligus, tanpa lelah dan tanpa jeda akhir pekan.

Pelajaran defensifnya juga bukan hal baru, tetapi menjadi jauh lebih mendesak:

- **Inventarisasi aplikasi pinggiran** — broker API, backend mobile karyawan, portal partner, dan sistem legacy adalah jalur masuk yang dipilih ARTEX, bukan aplikasi utama
- **Identitas adalah perimeter** — kredensial aplikasi, service principal, dan consent grant harus dimonitor seperti halnya kredensial user
- **Kecepatan deteksi menentukan** — jika waktu dari target awal ke privileged access bisa kurang dari 3 jam, alert yang hanya dibaca keesokan harinya sudah terlambat

**Jika Anda menjalankan aplikasi internet-facing, audit sekarang — terutama yang jarang diperhatikan.**
